# FlashFlow 架构说明

## 1. 系统有哪些服务

FlashFlow 采用多服务拆分（后续以 Spring Cloud 体系落地），当前规划如下：

| 服务 | 名称（规划） |
|------|----------------|
| API 网关 | `flashflow-gateway` |
| 用户服务 | `flashflow-user` |
| 商品服务 | `flashflow-product` |
| 订单服务 | `flashflow-order` |
| 抢购服务 | `flashflow-seckill` |
| 实时推送服务 | `flashflow-realtime` |

基础设施（非业务服务，但架构依赖）：MySQL、Redis、Kafka、Docker；Kubernetes 为后期可选。

## 2. 每个服务做什么

### 2.1 `flashflow-gateway`

- 对外唯一 HTTP/WebSocket 入口。
- 负责路由转发到各业务服务。
- 承担统一鉴权入口（校验登录凭证，再转发至下游）。

### 2.2 `flashflow-user`

- 用户登录与身份凭证签发/校验相关能力。
- 维护用户基础信息（登录所需最小集）。

### 2.3 `flashflow-product`

- 商品列表、商品详情等浏览能力。
- 维护普通商品与抢购活动商品的基础展示数据。
- 为订单/抢购提供商品信息查询能力。

### 2.4 `flashflow-order`

- 普通下单。
- 订单持久化与订单查询（列表/详情）。
- 维护订单状态流转，并在状态变更时对外发出事件。

### 2.5 `flashflow-seckill`

- 限时抢购入口与抢购流程编排。
- 在高并发场景下处理活动校验、热点库存扣减与抢购结果。
- 抢购成功后驱动订单创建（通过同步调用或异步消息，见第 3 节）。

### 2.6 `flashflow-realtime`

- 维护客户端实时连接（WebSocket）。
- 消费订单状态变更事件，并向对应用户推送最新状态。

## 3. 服务之间如何调用

整体调用关系（同步 + 异步）：

```text
Client
  │  HTTP / WebSocket
  ▼
Gateway
  ├─ HTTP → User        （登录）
  ├─ HTTP → Product     （商品浏览）
  ├─ HTTP → Order       （普通下单、订单查询）
  ├─ HTTP → Seckill     （限时抢购）
  └─ WS   → Realtime    （实时订单状态）

Seckill ──(同步 RPC/HTTP 或异步 Kafka)──► Order   （抢购成功后落单）
Order   ──(同步查询)──► Product                 （校验商品信息）
Order   ──(Kafka 事件)──► Realtime              （订单状态变更推送）
Seckill ──(读/写)──► Redis                      （活动与热点库存）
各业务服务 ──(读写)──► MySQL                     （持久化）
```

说明：

- **同步调用**：登录、浏览、下单、查询、抢购请求路径走 Gateway → 对应服务；订单创建前可同步查询商品服务。
- **异步调用**：订单状态变更由订单服务写入 Kafka；实时推送服务消费后推给客户端。抢购高峰也可将“创建订单”异步化，降低同步链路压力（实现阶段再定最终方案）。
- **客户端不直连**业务服务；一律经 Gateway。

## 4. MySQL 做什么

- 作为系统**权威持久化存储**。
- 主要承载：用户数据、商品主数据、订单与订单明细、抢购活动配置等需长期保存且需事务保证的数据。
- 普通下单、订单查询以 MySQL 中的订单数据为准。

## 5. Redis 做什么

- **缓存**：热点商品信息、活动信息等，减轻 MySQL 读压力。
- **抢购热点库存**：限时抢购场景下的库存预扣/计数，支撑高并发读写。
- **登录会话/Token 相关数据**（若采用服务端会话或黑名单等机制，可存放于此）。
- 不替代 MySQL 作为最终订单账本；关键结果最终仍需落库。

## 6. Kafka 做什么

- **异步解耦**：订单状态变更等事件从订单服务投递到消息队列。
- **削峰**：抢购成功后的订单创建、后续通知等可走异步，避免同步链路被打满。
- **事件驱动推送**：`flashflow-realtime` 消费订单相关 Topic，驱动 WebSocket 推送。

## 7. WebSocket 做什么

- 由 `flashflow-realtime` 提供长连接能力。
- 客户端经 Gateway 建立 WebSocket 连接并完成鉴权后，订阅本人订单状态。
- 当订单状态变化时，服务端主动推送最新状态，支撑“实时订单状态”需求。

## 8. 部署与后期选项（附）

- **Docker**：各服务与中间件容器化部署。
- **Kubernetes**：后期可选，用于编排与扩缩容；当前架构不依赖 K8s 才能成立。
